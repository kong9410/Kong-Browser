# kong-browser 설계 v2 — 페이지 안에서 재배치하는 브라우저

> 작성 2026-11-04. v1(추출 → 앱이 다시 그리는 뷰어)에서 **사이트를 그대로 열고 화면 배치만 바꾸는 브라우저**로 방향을 바꿨습니다.
> 0단계 프로토타입(v1 방식)은 M1 에서 transformer 로 대체되었고, 코드는 삭제했습니다.

## 1. 목표와 범위

**목표:** 어느 커뮤니티든 일반 브라우저처럼 접속하되, 게시판 목록, 게시글, 댓글이 항상 같은 배치와 같은 모양으로 보이게 한다.

**MVP 포함**
- 주소창, 뒤로/앞으로, 새로고침, 원본 보기 전환
- 게시판 목록, 게시글(본문, 베스트 댓글, 댓글, 대댓글)의 통일된 배치
- 루리웹, 디시인사이드 모바일 페이지
- 사이트 변경 감지, 원본 화면 대체, 자동 보고, 레시피 원격 업데이트

**MVP 제외:** 탭 여러 개, 북마크, 방문 기록, iOS, AI 학습/수리.
로그인과 글쓰기는 원본 기능이 그대로 동작하므로 따로 만들지 않아도 됩니다(검증은 M5).

## 2. 전체 구조

```
┌──────────────── Android 앱 (Kotlin) ────────────────┐
│  [주소창] [뒤로][앞으로][새로고침] [원본 보기]          │
│  ┌──────────── 시스템 WebView ─────────────────────┐ │
│  │  루리웹 페이지 (그대로 로드)                       │ │
│  │   + transformer.js  ← 앱에 내장된 엔진            │ │
│  │   + 레시피(JSON)    ← 서버에서 받아 캐시           │ │
│  │   → 원본 요소를 #kong-root 뼈대로 이동 + 공통 CSS  │ │
│  └────────────── KongBridge(JS↔앱) ────────────────┘ │
│  RecipeStore (로컬 캐시, 마지막 정상 버전 보관)        │
└──────────────────────┬──────────────────────────────┘
                       │ 레시피 동기화 / 고장 보고
┌──────────── Spring Boot (Kotlin) ───────────────────┐
│  Recipes API · Reports API · 알림 · (나중에) Learn/Repair│
│  PostgreSQL: recipe(버전 이력), report               │
└─────────────────────────────────────────────────────┘
        ▲ 레시피 수정·배포
┌───────┴────── 개발 PC: kong CLI (TypeScript) ─────────┐
│  browse(개발용 브라우저) · diagnose · check · publish    │
│  canary(정기 점검) · 스냅샷 보관                        │
└─────────────────────────────────────────────────────┘
```

역할 구분
- **엔진(transformer.js):** 앱에 내장된 코드. 앱을 업데이트할 때만 바뀝니다.
- **레시피:** 사이트별 셀렉터와 배치 정보를 담은 데이터. 서버에서 언제든 바뀝니다. 사이트가 바뀌었을 때 고치는 대상은 거의 항상 레시피입니다.
- **서버:** 레시피 배포와 고장 보고 수집만 합니다. 사이트 페이지나 콘텐츠는 다루지 않습니다.

## 3. 핵심 흐름

### 3-1. 레시피가 있는 페이지

```
1. 탐색 시작 → 앱이 URL 에 맞는 레시피가 있는지 확인
2. 문서 로드 시작 시점 (document-start)
   - 가림 CSS 주입: html { visibility: hidden }   ← 원본이 깜빡이지 않게
   - 안전장치 타이머: 2.5초 뒤 무조건 가림 해제
3. DOM 준비 완료 → transformer.run(recipe)
   ① 탐지: 레시피대로 모든 요소를 찾기만 함 (DOM 은 아직 건드리지 않음)
   ② 판정: ok / degraded / broken  (7-1절)
   ③ ok·degraded → 뼈대 생성, 원본 요소 이동, 나머지 숨김, 공통 CSS 적용
      broken      → 아무것도 바꾸지 않음
   ④ 가림 해제
4. 결과를 KongBridge 로 앱에 전달 → broken/degraded 면 보고 (7-2절)
5. 감시: 늦게 붙는 댓글 등은 MutationObserver 로 계속 뼈대 안으로 옮김
```

①과 ③을 분리한 이유는, 판정이 끝나기 전에는 DOM 을 한 글자도 바꾸지 않기 위해서입니다. 그래서 레시피가 깨져도 반쯤 망가진 화면이 나오지 않고, 원본이 온전히 보입니다.

### 3-2. 레시피가 없는 페이지

일반 브라우저와 똑같이 원본을 보여줍니다. AI가 정해지면 주소창 옆 [이 사이트 변환하기] 버튼이 생깁니다(M5).

### 3-3. 원본 보기

요소를 이미 옮긴 뒤라 되돌리기보다 **재배치 없이 새로고침**하는 쪽이 단순하고 확실합니다. 앱이 그 탭에서 주입을 끈 상태로 다시 로드합니다. 다시 누르면 원래대로 돌아옵니다.

### 3-4. 페이지 이동

링크는 원본 그대로이므로 클릭하면 일반 브라우저처럼 이동하고, 이동한 페이지에서 3-1 흐름이 다시 실행됩니다. 뒤로가기는 WebView 히스토리를 씁니다.

## 4. 통일 레이아웃 (뼈대)

모든 사이트가 아래 뼈대 안으로 들어갑니다. 슬롯마다 **채우는 방식**이 다릅니다.

- `text`: 원본에서 텍스트만 읽어 엔진이 만든 요소에 넣음. 모양을 완전히 통일할 수 있음
- `move`: 원본 노드를 통째로 옮김. 이미지 지연 로딩, 동영상, 버튼 이벤트가 그대로 동작

```
게시글 (#kong-root[data-page=post])
├─ header
│   ├─ site      사이트 이름                         (레시피 상수)
│   ├─ title     제목                                text
│   └─ meta      작성자 · 시각 · 조회 · 추천          text
├─ body          본문 컨테이너                        move  (exclude 로 서명/광고 제거)
├─ actions       추천/스크랩 등 원본 버튼 (선택)       move
├─ ad            원본 광고 영역 (선택)                move
├─ best          베스트 댓글 (있는 사이트만 표시)
│   └─ comment × n
├─ comments      댓글
│   ├─ comment × n
│   │   ├─ who / when                            text
│   │   ├─ content                               move  (이미지·디시콘 유지)
│   │   └─ actions  답글/추천 버튼 (선택)          move
│   └─ more      댓글 더보기 / 페이지 버튼 (선택)   move
└─ source        원본 링크

게시판 (#kong-root[data-page=board])
├─ header        게시판 이름                          text
├─ rows          글 행 × n: 제목·댓글수·작성자·시각·조회  text (+ 원본 href 로 만든 링크)
└─ pager         다음/이전 페이지                      move
```

### CSS 격리

- 원본 `body`의 다른 자식은 `display: none` 으로 숨깁니다. 지우지 않고 숨기는 이유는 사이트 JS가 그 요소를 찾을 수 있어야 하기 때문입니다.
- `#kong-root` 아래는 `all: revert` 로 사이트 스타일을 초기화한 뒤 공통 스타일을 적용합니다. 모든 규칙에 `#kong-root` 접두어를 붙여 우선순위를 확보합니다.
- **Shadow DOM 은 쓰지 않습니다.** 원본 노드를 Shadow DOM 안으로 옮기면 사이트 JS의 `document.querySelector` 가 그 노드를 못 찾아 기능이 깨집니다.
- 다크모드와 글자 크기는 CSS 변수로 두고, 앱 설정에서 바꿀 수 있게 합니다.

## 5. 레시피 스펙 v2

```jsonc
{
  "schemaVersion": 2,
  "host": "m.ruliweb.com",
  "version": 7,              // 서버가 배포할 때마다 +1
  "minEngine": 1,            // 이 레시피를 이해하는 최소 엔진 버전
  "siteName": "루리웹",
  "pages": [
    {
      "id": "post",
      "type": "post",
      "match": "/board/[0-9]+/read/[0-9]+",     // pathname+search 정규식
      "probe": [".board_main_view"],           // 이 페이지 유형이 맞는지 확인하는 표식
      "title":     { "sel": [".subject_inner_text", "h1.subject"], "required": true },
      "author":    { "sel": [".user_info .nick"] },
      "createdAt": { "sel": [".user_info .regdate"] },
      "views":     { "sel": [".user_info"], "pattern": "조회\\s*([0-9,]+)" },
      "likes":     { "sel": [".user_info .like"] },
      "body":      { "sel": [".view_content"], "required": true, "exclude": [".sign", ".btn_wrapper"] },
      "actions":   { "sel": [".board_main_view .btn_like"] },
      "ad":        { "sel": [".ad_slot"] },
      "commentCount": { "sel": [".comment_count"], "pattern": "([0-9]+)" },  // 검산용
      "comments": {
        "anchor":   ".comment_container",           // 사이트가 댓글 버튼 이벤트를 위임해 둔 상위 요소 (6절)
        "item":     ["tr.comment_element.normal"],
        "bestItem": ["tr.comment_element.best"],  // 기능이 없는 사이트는 생략
        "replyMarker": ".child",
        "who":     { "sel": [".nick"] },
        "when":    { "sel": [".time"] },
        "content": { "sel": [".text_wrapper .text"], "required": true },
        "more":    { "sel": [".comment_more"] }
      }
    },
    {
      "id": "board", "type": "board", "match": "^/[a-z]+/board/[0-9]+/?(\\?.*)?$", "probe": [".board_list_table"],
      "boardName": { "sel": ["strong#board_name"] },
      "rows": { "scope": [".board_main .board_list_table"], "item": ["tr.table_body.default_list"],
                "title": { "sel": [".subject_link"], "exclude": [".num_reply"] }, "link": { "sel": [".subject_link"] }, "...": "..." },
      "more":  { "sel": ["#btn_more"] },
      "pager": { "sel": [".paging_wrapper"] }
    }
  ]

```

실제로 동작하는 전체 레시피는 [recipes/m.ruliweb.com.json](../recipes/m.ruliweb.com.json) 입니다.

v1 대비 바뀐 점과 그 이유

| 변경 | 이유 |
|---|---|
| `sel` 이 배열 (앞에서부터 처음 맞는 것 사용) | 사이트가 일부만 바꾸거나 A/B 테스트 중일 때, 새 셀렉터를 앞에 추가하고 옛 셀렉터를 뒤에 남겨 양쪽을 모두 지원 |
| `probe` | 이 페이지가 정말 그 유형인지, 사이트 구조가 통째로 바뀌었는지를 먼저 확인 |
| `required` | 필수 요소가 없으면 broken, 선택 요소가 없으면 degraded 로 나눠서 판정 |
| `commentCount` 등 검산용 필드 | 셀렉터가 맞긴 맞는데 엉뚱한 걸 잡는 "조용한 고장"을 잡기 위함 (7-1절) |
| `minEngine` | 새 엔진 기능이 필요한 레시피를 구버전 앱이 받으면, 깨지는 대신 원본 화면으로 표시 |
| 같은 `type` 의 페이지를 여러 개 둘 수 있음 | 사이트가 일부 사용자에게만 새 디자인을 보여주는 기간에는 두 레시피를 함께 두고, `probe` 가 맞는 쪽을 사용 |
| `comments.anchor` (M1 에서 추가) | 사이트가 댓글 버튼 이벤트를 상위 요소에 위임해 두면, 버튼을 그 밖으로 옮기는 순간 동작하지 않음. anchor 를 통째로 옮기고 그 안에 댓글 목록을 만들어 해결 |
| `exclude` 를 text 필드에도 적용 | 제목 옆 "(7)" 같은 댓글 수 표시를 제목 텍스트에서 빼기 위함 (복제본에서 지우고 읽으므로 원본은 그대로) |
| `ad` 는 판정에서 제외 | 광고는 노출될 때도 안 될 때도 있어서, 없다고 degraded 로 보면 안 됨 |
| `rows.sameBoard` (M1 에서 추가) | 다른 게시판 글 링크도 "게시글 주소" 형식은 맞기 때문에, 게시판 식별자(예: `/board/([0-9]+)`)가 현재 페이지와 같은지 95% 이상 확인 |

## 6. transformer.js 엔진

```
transformer/ (TypeScript → esbuild 로 단일 파일 번들)
  hide.ts      document-start 용: 가림 CSS + 안전장치 타이머
  locate.ts    레시피대로 요소 탐지 (DOM 변경 없음)
  judge.ts     ok / degraded / broken 판정 + 검산
  layout.ts    뼈대 생성, 원본 요소 이동, 원본 숨김
  observe.ts   늦게 붙는 요소 감시 및 이동
  style.css    공통 스타일 (번들에 포함)
  index.ts     window.kong = { run(recipe), status() }
```

- 엔진 버전은 정수 하나(`ENGINE_VERSION`)로 관리합니다. 레시피의 `minEngine` 과 비교합니다.
- **실행 시점 (M1 에서 확인):** 사이트는 보통 DOM 준비 직후(jQuery ready 등)에 `$('.board_main_view .like').click(...)` 처럼 *셀렉터로* 이벤트를 붙입니다. 그보다 먼저 요소를 옮기면 이벤트가 아예 안 붙습니다. 그래서 DOMContentLoaded 뒤 매크로태스크 두 번을 양보한 뒤 실행합니다(사이트 초기화가 끝난 다음).
- **이벤트가 살아남는 두 조건:** ① 요소에 직접 붙은 이벤트는 옮겨도 따라옴(실행 시점만 지키면 됨) ② 상위 요소에 위임된 이벤트는 그 상위 요소 안에 있어야 함 → `anchor`.
- 실행 중 예외는 전부 잡아서 broken 으로 처리하고, 가림을 해제합니다. 엔진 버그가 있어도 사용자는 원본을 볼 수 있어야 합니다.
- 같은 번들을 Android 앱, 개발 PC 도구, 나중에 iOS 앱이 똑같이 씁니다.

## 7. 사이트 변경 대응 ★

커뮤니티 사이트는 예고 없이 바뀝니다. 목표는 **망가진 화면이 사용자에게 보이지 않게 하고(안전), 고장을 빨리 알아채고(감지), 앱 업데이트 없이 고치는 것(복구)** 입니다.

```
 사이트 변경
   │
   ▼
[1 감지] 앱이 매 페이지 판정 ──┬── broken  → 원본 표시 + 배너
         개발 PC 카나리 점검    └── degraded → 재배치하되 빠진 정보는 숨김
   │
   ▼
[2 보고] 앱 → 서버 (콘텐츠 없이 "어느 레시피의 어느 필드가 실패" 만)
   │
   ▼
[3 알림] 서버: 같은 레시피 실패가 기준을 넘으면 → 나에게 알림
   │
   ▼
[4 수리] 개발 PC: diagnose 로 원인 확인 → 레시피 수정 → check 로 회귀 검증
   │
   ▼
[5 배포] publish → 서버 버전 +1 → 앱이 받아서 즉시 적용 (앱 업데이트 불필요)
   │
   ▼
[6 확인] 새 버전 보고가 정상이면 끝. 문제가 생기면 rollback
```

### 7-1. 감지: 판정 기준

| 판정 | 조건 | 사용자에게 보이는 것 |
|---|---|---|
| **ok** | probe 일치, 필수·선택 필드 모두 찾음, 검산 통과 | 통일 화면 |
| **degraded** | probe 일치, 필수 필드는 있음, 선택 필드 일부 없음 또는 검산 경고 | 통일 화면 (빠진 정보는 표시 안 함) |
| **broken** | probe 불일치, 필수 필드 없음, 엔진 예외, `minEngine` 미달 | **원본 화면** + 상단 배너 "이 사이트 화면이 바뀌어 원래 화면으로 보여드려요" |

**조용한 고장 잡기 (검산).** 셀렉터가 "찾기는 찾는데 엉뚱한 것"을 잡는 경우가 가장 위험합니다. 그래서 다음을 확인합니다.
- 제목: 1~300자, 사이트 이름과 같지 않음
- 본문: 텍스트가 있거나 이미지/동영상이 1개 이상
- 댓글: 페이지에 표시된 댓글 수(`commentCount`)와 찾은 댓글 수의 차이가 크면 경고
- 게시판: 행이 3개 이상, 행 링크의 80% 이상이 같은 사이트 post 레시피의 `match` 에 맞음 (사이드바 목록이 섞이는 문제 방지)
- 같은 셀렉터가 여러 개를 찾으면 안 되는 필드(title, body)가 여러 개를 찾으면 경고

**변경 감지의 기본은 앱 자체입니다.** 앱은 레시피가 있는 페이지를 열 때마다(첫 방문뿐 아니라 매번) 위 판정을 실행합니다. 사용자는 아무것도 설치하거나 설정할 필요가 없습니다. 깨졌으면 그 자리에서 원본 + 배너를 보여주고, 보고를 남깁니다(7-2). 친구·지인이 쓰기 시작하면 **그들의 평소 방문이 곧 점검**이 되고, 보고가 서버로 모여 알림이 갑니다(M4).

**카나리 점검 (개발자 PC, 선택).** 아무도 그 사이트에 들어가지 않은 날에도 미리 알고 싶을 때 쓰는 보조 장치입니다. 사용자 앱과는 무관하고, 앱 배포에 필요하지 않습니다.
- `npm run canary` 가 각 사이트 게시판 첫 페이지와 최신 글 5개에 레시피를 적용해 판정합니다.
- 서버가 아니라 개발자 PC에서 돌리는 이유는, 서버(클라우드) IP는 커뮤니티 사이트에 막히기 쉽기 때문입니다. 필요하면 개발자 PC 의 작업 스케줄러로 매일 돌립니다.

### 7-2. 보고

앱은 판정이 ok 가 아니면 서버로 보냅니다.

```json
{ "host": "m.ruliweb.com", "recipeVersion": 7, "pageId": "post",
  "verdict": "broken", "failed": ["probe", "title"], "warnings": [],
  "urlPath": "/board/300143/read/*", "engine": 1, "app": "0.3.0" }
```

- **콘텐츠는 보내지 않습니다.** 제목, 본문, HTML 모두 제외합니다. URL도 글 번호를 `*` 로 지워서 보냅니다.
- 같은 레시피, 같은 실패는 기기당 1시간에 1번만 보냅니다.

### 7-3. 알림

서버는 같은 (host, recipeVersion, pageId) 에 대해 **1시간 안에 broken 보고 3건 이상**(사용자 앱에서 온 보고) 또는 **카나리 실패**가 들어오면 알립니다. 사용자가 나 혼자인 단계에서는 보고 1건만으로도 알리도록 기준을 낮춥니다. 알림 채널(Discord/Telegram 웹훅, 이메일 등)은 M4 때 정합니다.

### 7-4. 수리 (개발 PC 도구)

| 명령 | 하는 일 |
|---|---|
| `kong diagnose <url>` | 모바일 에뮬레이션으로 페이지를 열고, 레시피의 각 필드가 무엇을 찾았는지/못 찾았는지 표로 보여줌. 실패한 필드 주변의 정리된 HTML 을 출력해서 새 셀렉터를 찾기 쉽게 함 |
| `kong browse <url>` | 화면이 보이는 개발용 브라우저(모바일 에뮬레이션)를 열고 모든 페이지에 엔진+레시피를 주입. 레시피 파일을 저장하면 자동 새로고침 |
| `kong check <recipe>` | 저장해 둔 스냅샷 HTML 전부 + 실시간 샘플 URL 에 레시피를 돌려서 회귀 확인 |
| `kong snapshot <url>` | 판정 ok 인 페이지의 HTML 을 개발 PC 에 저장 (회귀 테스트 자료. 서버에는 올리지 않음) |

**수리 원칙**
- 새 셀렉터는 `sel` 배열의 **앞에 추가**하고, 옛 셀렉터는 당분간 남깁니다. 사이트가 점진적으로 배포하는 동안 양쪽 페이지를 모두 처리할 수 있습니다.
- 사이트가 통째로 개편됐으면 새 page 항목을 추가하고 `probe` 로 구분합니다. 옛 항목은 보고가 사라지면 지웁니다.
- 스냅샷은 사이트마다 페이지 유형별로 다양하게 모읍니다(이미지 글, 동영상 글, 댓글 없는 글, 공지, 대댓글 많은 글).

### 7-5. 배포와 반영

**레시피 업데이트 (대부분의 경우)**
- `kong publish <recipe>` → 서버가 버전 +1 로 저장합니다. 이전 버전은 모두 보관합니다.
- 앱이 새 레시피를 받는 시점은 세 가지입니다.
  - 앱 시작 시
  - 6시간마다 (WorkManager)
  - **broken 을 만난 즉시** 해당 사이트만 확인. 이미 고쳐져 있다면 그 자리에서 다시 적용합니다.
- 앱은 마지막으로 ok 를 낸 버전(last-known-good)을 따로 보관합니다. 새 버전이 깨지면 그 버전으로 다시 시도합니다.
- `kong rollback <host> <version>` 으로 서버 쪽 활성 버전을 되돌릴 수 있습니다.

**엔진 업데이트 (드문 경우)**
사이트가 레시피로 표현할 수 없는 방식으로 바뀌면 엔진에 기능을 추가하고 앱을 업데이트합니다. 예를 들면 댓글을 특별한 방식으로 불러오는 경우입니다. 새 기능을 쓰는 레시피는 `minEngine` 을 올려서, 구버전 앱은 깨지는 대신 원본 화면을 보여주게 합니다.

**왜 레시피에 사이트별 JS를 허용하지 않는가**
- **보안:** 레시피에 JS를 넣을 수 있으면, 서버가 해킹당했을 때 모든 사용자의 커뮤니티 페이지에서 임의 코드가 실행됩니다. 나중에 로그인 기능을 쓰면 쿠키가 탈취될 수 있습니다. 선언형 셀렉터만 허용하면 최악의 경우라도 화면이 이상해지는 수준에서 끝납니다.
- **스토어 정책:** 원격으로 받은 코드로 앱 동작을 바꾸는 것은 스토어 정책상 문제가 될 수 있습니다. 데이터만 받는 구조라면 안전합니다.
- 사이트 전용 처리가 꼭 필요하면 엔진에 이름 붙은 기능으로 추가합니다(예: `"commentLoader": "dc-ajax"`). 그 기능은 앱 업데이트로 배포합니다.

### 7-6. AI가 정해진 뒤 (M5)

AI의 가장 큰 가치는 처음부터 학습하는 것보다 **수리**에 있습니다. 옛 레시피, 실패한 필드, 정리된 HTML 을 주고 "바뀐 부분만 고친 레시피"를 받으면, 4단계 수리가 "AI 제안 → check → publish" 로 줄어듭니다. 이때도 사용자 기기의 HTML 은 [수리 요청] 버튼을 눌렀을 때만 보내고, 텍스트는 최소화합니다.

## 8-1. PC 브라우저 (Electron) — M3

크롬 엔진(Chromium)을 내장한 독립 프로그램입니다. 화면 구성은 직접 만들고, 웹페이지 영역은 Chromium 이 그립니다.

```
┌──────────── BrowserWindow ────────────────────────────┐
│ 툴바 (렌더러: TypeScript)                               │
│  [←][→][↻] [주소창 ..............] [원본 보기] [⚙]      │
│  판정 배너: "화면이 바뀌어 원래 화면으로 보여드려요"       │
├───────────────────────────────────────────────────────┤
│ WebContentsView  ← 실제 웹페이지                        │
│   preload: transformer.js + kong.boot(레시피)           │
│            (격리된 world 에서 실행, document-start)      │
└───────────────────────────────────────────────────────┘
 main 프로세스: 창/탭 관리, RecipeStore, 보고, (M4) 서버 동기화
```

| 영역 | 선택 | 이유 |
|---|---|---|
| 페이지 영역 | `WebContentsView` (툴바와 분리) | 툴바는 우리 코드, 페이지는 사이트 코드. 서로 섞이지 않게 |
| 엔진 주입 | 페이지의 **preload 스크립트**에서 실행 | 페이지 스크립트보다 먼저 실행되어 깜빡임 방지(document-start)가 자연스럽게 됨 |
| 실행 공간 | **격리된 world (contextIsolation)** | 엔진은 DOM API 만 쓰므로 사이트 JS 와 전역 변수를 공유할 필요가 없음. 사이트 스크립트가 엔진을 건드리거나, 엔진이 사이트 전역을 오염시키지 못함. DOM 과 이벤트 루프는 공유되므로 "사이트 초기화 뒤 실행" 규칙은 그대로 유효 |
| 엔진 ↔ 앱 | preload 의 `ipcRenderer` 로 판정 결과 전달 (Android 의 KongBridge 와 같은 역할) | |
| 원본 보기 | 다음 로드 한 번만 주입을 끄고 새로고침 | 3-3절과 동일 |
| 레시피 | 앱 리소스에 내장 → M4 에서 서버 동기화 + last-known-good | |
| 툴바 UI | 프레임워크 없이 TypeScript + CSS 로 시작 | 화면이 작아서 충분. 커지면 그때 도입 |
| 빌드/배포 | `electron-builder` 로 Windows 설치 파일 | |
| 보안 | 페이지 쪽 `nodeIntegration: false`, `sandbox: true` | 커뮤니티 페이지에서 PC 파일에 접근할 수 없게 |

저장소에는 `desktop/` 폴더로 추가하고, `transformer/` 의 번들과 `recipes/` 를 빌드 시 복사해서 씁니다.

**MVP 기능:** 주소창(URL 또는 검색어), 뒤로/앞으로/새로고침, 원본 보기 전환, 판정 배너, **탭**(2026-11-04 추가: 탭 줄, [+]/×/가운데 클릭, Ctrl+T/W/Tab/1~9, 새 창 링크는 새 탭, Ctrl+클릭은 뒤쪽 탭, 마지막 탭을 닫으면 창 닫힘, 탭마다 원본 보기 상태 따로). 탭 끌어서 순서 바꾸기, 다시 실행 시 탭 복원, **북마크**(☆/Ctrl+D, 북마크 바, 시작 페이지), **방문 기록**(Ctrl+H 페이지: 날짜별·검색·삭제, 시작 페이지 최근 방문)도 2026-11-04 추가. 모두 이 PC 의 `%APPDATA%/Kong Browser` 에만 저장하고 서버로 보내지 않음. 앱 안쪽 페이지(시작·방문 기록)만 기록/북마크 API 를 쓸 수 있도록 preload 와 main 양쪽에서 주소를 확인.

## 9. 서버 (Spring Boot 3 + Kotlin)

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/recipes?since={syncVersion}` | 변경된 레시피만 |
| GET | `/api/recipes/{host}` | 사이트 하나 (broken 즉시 확인용) |
| PUT | `/api/recipes/{host}` | 배포 (버전 +1) |
| POST | `/api/recipes/{host}/rollback` | `{version}` 을 활성으로 |
| GET | `/api/recipes/{host}/history` | 버전 이력 |
| POST | `/api/reports` | 고장 보고 |
| GET | `/api/reports/summary` | 사이트·버전별 판정 집계 (상태 확인용) |
| POST | `/api/learn`, `/api/repair` | AI 결정 전까지 `501` |

- 인증: 고정 토큰 헤더 `X-Kong-Token`. 앱은 읽기와 보고 권한, CLI 는 배포 권한으로 토큰 두 개를 둡니다.
- AI 연결부는 `RuleLearner` / `RecipeRepairer` 인터페이스로만 둡니다.

```
recipe (host, version, body jsonb, status[active|retired], source[manual|ai:*],
        sync_version bigserial, published_at)          -- 이력 전부 보관
report (id, host, recipe_version, page_id, verdict, failed jsonb, warnings jsonb,
        url_path, engine, app, created_at)
```

배포는 `docker compose` (서버 + PostgreSQL)로 하고, 호스팅 위치는 M4 때 정합니다.

## 12. 법적 고려

- 개인과 지인이 쓰는 범위입니다. 브라우저 안에서 표시만 바꾸는 것은 읽기 모드나 광고 차단기와 같은 성격이라 위험이 낮습니다.
- **콘텐츠를 서버로 보내거나 저장하지 않습니다.** 레시피는 셀렉터, 보고는 실패 정보뿐입니다. 스냅샷은 개발 PC 에만 둡니다.
- 사이트 광고는 기본적으로 뼈대 안에 남깁니다. 원본 링크는 항상 표시합니다.
- 공개 배포를 하게 되면 그때 법률 검토가 필요합니다. 브라우저 안에서 DOM 을 바꾸는 행위 자체를 다툰 해외 판례(독일 광고 차단기 사건)가 있습니다.

## 12-1. 테스트 원칙 (2026-11-04, 사용자 결정)

| 종류 | 무엇 | 언제 |
|---|---|---|
| **단위 테스트** | 함수·모듈 단위. 실제 앱이나 실제 사이트 없이 빠르게 (예: 엔진의 탐지·판정·메뉴 읽기를 HTML 조각 + 가짜 DOM 으로, `store.ts`, 주소 처리 함수) | **구현할 때마다.** 구현 검증은 단위 테스트로만 |
| **통합 테스트** | `desktop` `npm run e2e` (실제 앱), `transformer` `npm run check` (실제 브라우저로 스냅샷), `canary`, 실제 사이트 확인 | **큰 작업이 끝났을 때 또는 커밋 전에 한 번** |

사이트 화면 구조를 살펴 레시피를 *작성*하는 것은 테스트가 아니므로 필요할 때 한다.
